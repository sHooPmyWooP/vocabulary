# Vocabulary

Vocabulary is a single-user, self-hosted web app for collecting unfamiliar English words and phrases, then learning them with spaced repetition.

The app is designed for a simple reading workflow:

1. Enter an unfamiliar word or phrase.
2. Read its English definition, examples, and synonyms where available.
3. The successful lookup is automatically added to your review deck.
4. Review due cards later and grade your recall with **Again**, **Hard**, **Good**, or **Easy**.

> The app keeps English dictionary definitions as the authoritative source and can enrich each sense with a context-aware German translation generated by Azure AI Foundry.

## Features

- Look up individual English words and multi-word phrases
- Generate and cache German translations with Azure AI Foundry
- Automatically save successful lookups
- Avoid duplicates through case-insensitive, whitespace-trimmed matching
- Count repeated lookups of the same entry
- Undo a lookup or delete an entry
- Show the vocabulary source after lookup and on every review card
- Review cards with an SM-2 spaced-repetition scheduler
- Limit new cards to 20 per review session while keeping all due reviewed cards available
- Browse, search, sort, edit, annotate, and delete saved entries
- View deck size, due cards, maturity, review activity, and accuracy
- Responsive light and dark UI
- Persist everything in SQLite
- Run locally or as one Docker container

## How definitions and “translation” work

Vocabulary uses two public English dictionary sources and normalizes both into the same internal representation.

### Source routing

| Input | Primary source | Behavior |
|---|---|---|
| Single word, such as `run` | [Free Dictionary API](https://dictionaryapi.dev/) | Returns English parts of speech, definitions, examples, and synonyms |
| Phrase or idiom, such as `kick the bucket` | [English Wiktionary](https://en.wiktionary.org/) | Returns English definitions and examples |

A phrase is any normalized input containing more than one whitespace-separated word.

For single words, the Free Dictionary API is tried first. Wiktionary is then tried when the first provider has no entry or is temporarily unavailable. Azure AI Foundry is the final fallback when neither dictionary can provide a usable result.

### Lookup pipeline

1. **Normalize the input**
   - Leading and trailing whitespace is removed.
   - Text is converted to lowercase.
   - Internal spaces are preserved.
   - For example, ` Run ` becomes `run`.

2. **Choose a dictionary source**
   - One word goes to the Free Dictionary API.
   - Multiple words go to Wiktionary.

3. **Resolve phrases when necessary**
   - Wiktionary is queried using the exact phrase first.
   - If no exact page exists, the MediaWiki search API finds likely page titles.
   - The first candidate with usable English definitions is selected.
   - This allows loose input such as `cut the corner` to resolve to a canonical entry such as `cut corners`.

4. **Parse the response**
   - Free Dictionary API meanings are converted into senses with parts of speech, definitions, examples, and synonyms.
   - Wiktionary HTML definitions are flattened to plain text.
   - Only Wiktionary's English section is used.
   - Wiktionary's definition endpoint does not provide synonyms in the shape used by this app, so phrase entries commonly have no synonyms.

5. **Convert to the canonical format**

   Both providers are converted to the same source-independent structure before storage:

   ```json
   {
     "schema": "canonical/1",
     "word": "run",
     "senses": [
       {
         "part_of_speech": "verb",
         "definitions": [
           {
             "definition": "To move rapidly on foot.",
             "example": "I run every morning."
           }
         ],
         "synonyms": ["sprint", "dash"]
       }
     ]
   }
   ```

6. **Use the AI fallback when both dictionaries fail**
   - Foundry checks whether the input is an established English word, inflection, idiom, or meaningful phrase.
   - Recognized input receives generated English senses, examples, synonyms, and German translations.
   - Understandable slang, vulgar expressions, and productive informal formations are accepted.
   - Random gibberish, meaningless misspellings, and standalone proper nouns are rejected.
   - Generated definitions are clearly marked in lookup and review screens.

7. **Save the entry**
   - Successful dictionary or Foundry lookups are inserted into SQLite and become due immediately.
   - Existing normalized words are not duplicated. Their lookup count is incremented instead.
   - Input rejected by every provider is not saved.

The canonical format is the provider-normalization layer. The UI and review system do not need to know which external dictionary produced an entry.

### German translation with Azure AI Foundry

After a successful dictionary lookup, the app sends the word and its English senses to the configured Azure AI Foundry model. The model returns one concise German translation and one short German explanation per sense. Sense indexes are validated so translations cannot silently attach to the wrong meaning.

When both dictionaries fail, Foundry becomes a complete lexicographic fallback. It generates the English definition data required by the flashcard as well as the German translation. These entries store `"source": "azure-ai-foundry"` and `"generated": true` and are visibly labeled **AI-generated definition**.

The lookup result and every review card identify the source as **Free Dictionary API**, **Wiktionary**, or **Azure AI Foundry**.

Generated data is stored inside the canonical payload:

```json
{
  "translations": {
    "de": {
      "provider": "azure-ai-foundry",
      "senses": [
        {
          "translation": "laufen",
          "explanation": "Sich schnell zu Fuß bewegen."
        }
      ]
    }
  }
}
```

Translations are generated only when an entry does not already have one. They are then reused during lookup and review, avoiding repeated model calls. If Foundry is not configured, unavailable, or returns malformed output, the English dictionary lookup still succeeds without a German translation.

The English definitions themselves are never generated or rewritten by the model. Provider-specific metadata such as pronunciation data is not currently preserved.

## Review scheduling

New entries are due on the day they are added. Reviews use a four-button interface mapped to SM-2 quality scores:

| Button | SM-2 quality | Result |
|---|---:|---|
| Again | 0 | Reset repetitions and schedule for 1 day later |
| Hard | 3 | Successful recall with a strong ease penalty |
| Good | 4 | Successful recall with a small ease penalty |
| Easy | 5 | Successful recall with an ease increase |

Intervals progress as follows for successful reviews:

- First successful review: 1 day
- Second consecutive successful review: 6 days
- Later successful reviews: current interval multiplied by the current ease factor

The ease factor starts at `2.5` and never falls below `1.3`.

Card states are:

- **New:** never reviewed
- **Learning:** reviewed with an interval shorter than 21 days
- **Mature:** interval of at least 21 days

Review sessions include every reviewed card due on or before today. New cards are capped at 20 per session. Cards are ordered by oldest due date first and randomized within the same due date.

## Application pages

| Route | Purpose |
|---|---|
| `/` | Overview of total words and cards due today |
| `/lookup` | Look up and automatically save a word or phrase |
| `/review` | Review due cards and update their schedules |
| `/browse` | Search, sort, edit, annotate, and delete entries |
| `/stats` | View deck maturity, accuracy, and the last 30 days of review activity |

The frontend uses server-rendered Jinja templates and HTMX. There is no JavaScript build step or SPA framework. HTMX is loaded from the `unpkg.com` CDN, so interactive partial-page updates require browser access to that CDN.

## Architecture

```text
Browser
  |
  | HTML forms and HTMX requests
  v
FastAPI routes                         app/main.py
  |
  +--> dictionary lookup and parsing  app/dictionary_client.py
  |
  +--> German translation             app/translation_client.py
  |
  +--> SQLite persistence             app/vocab_store.py
  |       |
  |       +--> schema and connection  app/db.py
  |
  +--> SM-2 scheduling                app/scheduler.py
  |
  +--> statistics aggregation         app/stats.py
  |
  +--> Jinja templates                app/templates/
```

The scheduler and statistics modules are pure Python logic with no HTTP or database access. External dictionary details are isolated inside `dictionary_client.py`, while Foundry integration lives in `translation_client.py`. SQLite access is isolated inside `vocab_store.py` and `db.py`.

## Data model

### `entries`

Stores the saved vocabulary and current scheduling state:

- normalized word or resolved phrase
- canonical dictionary payload as JSON
- creation timestamp
- lookup count
- ease factor
- interval in days
- repetition count
- next due date
- maturity state
- optional user note

### `review_log`

Stores one row per grade:

- entry ID
- review timestamp
- grade

Deleting an entry also deletes its review history through a foreign-key cascade.

## Requirements

- Python 3.12 or newer
- [uv](https://docs.astral.sh/uv/)
- Internet access from the server for dictionary lookups
- Internet access from the browser for the HTMX CDN

No dictionary API key is required.

## Local development

Install dependencies:

```bash
uv sync
```

Start the development server:

```bash
uv run uvicorn app.main:app --reload
```

Or use the Makefile:

```bash
make install
make dev
```

Open <http://localhost:8000>.

The default database path is `data/vocab.db`. Override it with:

```bash
VOCAB_DB_PATH=/path/to/vocab.db uv run uvicorn app.main:app --reload
```

To reuse the Mealie agent's Foundry credentials locally without copying its secret, export that environment before starting Vocabulary:

```bash
set -a
source /home/david/repos/other/mealie-agent/.env
set +a
uv run uvicorn app.main:app --reload
```

The Mealie `.env` already supplies `AZURE_MODEL_FOUNDRY_KEY`. Vocabulary uses the same default endpoint and model as that project.

## Docker

Build the image:

```bash
docker build -t vocabulary .
```

Run it with a named volume:

```bash
docker run -d \
  --name vocabulary \
  --env-file /home/david/repos/other/mealie-agent/.env \
  -p 8000:8000 \
  -v vocab-data:/data \
  vocabulary
```

The container stores SQLite at `/data/vocab.db`. Mounting `/data` is essential if the vocabulary should survive container replacement.

Equivalent Makefile commands:

```bash
make docker-build
make docker-run ENV_FILE=/home/david/repos/other/mealie-agent/.env
make docker-stop
```

The following variables can be overridden:

```bash
make docker-run IMAGE=my-vocabulary PORT=8080 VOLUME=my-vocab-data
```

## Configuration

| Setting | Default | Description |
|---|---|---|
| `VOCAB_DB_PATH` | `data/vocab.db` locally, `/data/vocab.db` in Docker | SQLite database location |
| `AZURE_MODEL_FOUNDRY_KEY` | none | API key required to enable German translation |
| `AZURE_FOUNDRY_BASE_URL` | `https://ddas-foundry-test.services.ai.azure.com/openai/v1` | OpenAI-compatible Azure AI Foundry endpoint |
| `AZURE_FOUNDRY_MODEL` | `gpt-4.1-mini` | Foundry model used for translation |
| `PORT` | `8000` | Makefile port override |
| `IMAGE` | `vocabulary` | Docker image and container name used by the Makefile |
| `VOLUME` | `vocab-data` | Docker volume used by the Makefile |
| `ENV_FILE` | empty | Optional Docker env file passed by the Makefile |

The daily new-card limit is currently the code constant `DEFAULT_NEW_CARD_LIMIT` in `app/vocab_store.py`.

## Operational notes

- The app has no authentication and is intended for a trusted private network.
- SQLite schema creation and additive migrations run automatically at startup.
- Back up the SQLite database file or Docker volume to preserve vocabulary and review history.
- Dictionary availability and content quality depend on the external providers.
- If dictionary providers are unavailable, Foundry is attempted before a retryable error is shown.
- AI-generated definitions can be wrong despite validation and are visibly labeled in the UI.
